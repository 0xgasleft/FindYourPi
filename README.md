# Pi Hunter

Find your place in π. Enter a number, name, date, or word — it's
deterministically converted into digits, searched against a versioned,
publicly auditable π dataset, and if it's found, the specific occurrence can
be claimed as a cryptographically verified, permanent on-chain collectible.

**Status: all 9 build phases implemented and verified end-to-end**, including
a live run of the complete loop — real π digits, real search, real Merkle
proof, real on-chain mint, real indexed discovery page — against a local
chain and a real Postgres instance. See "What's real vs. what's deferred"
below for the honest boundary.

## Monorepo layout

```text
apps/web        Next.js frontend — landing/search, wallet + claim flow,
                 discovery/leaderboard/profile pages, dynamic OG images
apps/api        Fastify API — search, proof construction, discovery/
                 profile/leaderboard/metadata/artwork endpoints
apps/indexer    Watches PiHunterNFT's on-chain events, syncs Postgres
apps/admin      Not yet built (see "What's deferred" below)

packages/contracts   PiHunterNFT, PiDatasetRegistry, MerkleVerifierV1 (Hardhat + Solidity)
packages/pi-core     Canonical conversion, discoveryId, rarity/achievability — the
                     shared source of truth imported by web/api/contracts tests
packages/pi-search   Reproducible π digit generation (Chudnovsky binary splitting),
                     chunking + Merkle commitment, suffix-array search index
packages/proofs      Proof construction + a standalone verifier, independent of apps/api
packages/types       Shared TS types + contract ABIs (re-exported from compiled artifacts)
packages/config      Shared tsconfig base + Tailwind preset

infrastructure/docker  Local Postgres via docker-compose
docs/                  Architecture, threat model, proof system, rarity design
```

## The real π dataset (v1)

Not a placeholder. Generated by `packages/pi-search`'s own reproducible
Chudnovsky binary-splitting implementation (no downloaded digit file, no
external pi library), validated against a known-correct 150-digit reference
in its own test suite, then chunked and Merkle-committed:

```text
Version:         1
Digits:          50,000,000
Chunk size:      128 digits (packed 4-bit/digit)
Merkle root:     0x1a78fd7be42cced1c1378bd27df6eda7204e40dd0e3927c591cc4d72ec2c2338
Dataset hash:    0x756c307a8835c48601c33d866e7db1fabf498e85a38a2de77f3357187c2a8988
Algorithm:       chudnovsky-binary-splitting
```

This is smaller than the spec's aspirational "first billion digits" — 50M is
what's actually reproducible end-to-end (generation + chunking + indexing)
in a single development pass; see `docs/architecture.md` §5 for the honest
reasoning. `docs/rarity.md`'s achievability math is computed from whatever
`digitsIndexed` actually is, so raising this in a future v2/v3 doesn't
require touching that logic.

Reproduce it yourself: `pnpm --filter @pi-hunter/pi-search generate` (~4-5
minutes). Independently verify a published dataset without trusting this
repo's other tooling: `pnpm --filter @pi-hunter/pi-search verify` — this
regenerates every digit from scratch and re-derives the Merkle root,
confirming both from first principles.

## Local development

Requirements: Node 20+, pnpm 10+, Docker (for Postgres).

```bash
cp .env.example .env
pnpm install
pnpm --filter @pi-hunter/pi-search generate   # ~4-5 min; produces packages/pi-search/data/v1
pnpm --filter @pi-hunter/contracts compile

docker compose -f infrastructure/docker/docker-compose.yml up -d
pnpm --filter @pi-hunter/api migrate

# Terminal 1: local chain
pnpm --filter @pi-hunter/contracts node

# Terminal 2: deploy contracts + register the dataset against it
pnpm --filter @pi-hunter/contracts deploy:localhost
# copy the printed NFT_CONTRACT_ADDRESS / DATASET_REGISTRY_ADDRESS into .env

# Terminal 3: API (loads the dataset, serves search/proof/discovery/etc.)
pnpm --filter @pi-hunter/api dev

# Terminal 4: indexer (keeps Postgres in sync with on-chain claims)
pnpm --filter @pi-hunter/indexer dev

# Terminal 5: web
pnpm --filter @pi-hunter/web dev   # http://localhost:3000
```

Every one of these commands has actually been run, against real Postgres
and a real local chain, as part of building this project — not just written
and assumed to work.

## Deploying `apps/web` to Vercel

Vercel hosts the frontend only. `apps/api`, `apps/indexer`, and Postgres are
long-running processes (the API holds the ~50M-digit dataset in memory) —
they need a real host (Railway/Render/Fly.io/a VPS + managed Postgres, etc.),
not Vercel's serverless model. Deploy those separately first if you want a
fully working live site; without them, the deployed frontend still renders
(landing page, 3D hero, static pages) but search/claim will show the honest
"π is being difficult right now" error state rather than fabricating a result.

**Vercel project settings:**
- **Root Directory:** `apps/web` (this is a pnpm workspace monorepo — Vercel
  auto-detects `pnpm-workspace.yaml` at the repo root and runs the install
  from there; you don't need a custom install/build command).
- **Framework Preset:** Next.js (auto-detected).
- **Environment Variables** (Project Settings → Environment Variables):
  - `NEXT_PUBLIC_API_URL` — your deployed `apps/api` URL.
  - `NEXT_PUBLIC_NFT_CONTRACT_ADDRESS` — the deployed `PiHunterNFT` address.
  - `NEXT_PUBLIC_CHAIN_ID` — `84532` for Base Sepolia, `8453` for Base mainnet.
  - `NEXT_PUBLIC_RPC_URL` — optional, only needed to override the default
    public Base Sepolia RPC.

**Before pushing:** contract ABIs consumed by the frontend
(`packages/types/src/generated/*.abi.json`) are committed snapshots, not
read live from `packages/contracts/artifacts` (a gitignored Hardhat build
output) — this is what makes the Vercel build work without a Solidity
toolchain at all. If you change a contract's public interface, regenerate
them before committing:
```bash
pnpm --filter @pi-hunter/contracts compile
pnpm --filter @pi-hunter/types sync-abis
```

Nothing in `.env.example` is a real secret (see the comment at its top) —
the only field that ever holds sensitive material is `DEPLOYER_PRIVATE_KEY`,
which is used solely by `packages/contracts`' Hardhat config for local/testnet
deployment and is never read by `apps/web` or exposed to the browser.

## What's real vs. what's deferred

Built, tested, and independently verified in this pass:

* Reproducible π generation, chunking, Merkle commitment, suffix-array
  search — all with passing unit tests (`packages/pi-core`, `packages/pi-search`, 61 tests).
* Proof construction + standalone verification (`packages/proofs`, 8 tests),
  matched exactly by the on-chain verifier.
* `PiHunterNFT` / `PiDatasetRegistry` / `MerkleVerifierV1` — 14 Hardhat
  tests covering mint, duplicate-claim rejection, invalid-proof rejection,
  dataset deactivation semantics, access control, pause, the full
  commit-reveal path, and tokenURI.
* Real measured gas for `claim()`: ~192,000–195,000 gas (docs/proof-system.md §4.1).
* Full API (search/proof/discovery/metadata/artwork/leaderboard/profile),
  10 tests, including a security-review regression test for a malformed-input bug found and fixed during review (see `docs/threat-model.md`).
* Complete frontend: search UX, wallet connect, claim flow, public discovery
  page with dynamic OG images, leaderboard, profile pages — all wired to
  the real API and a real deployed contract, not mocked.
* A live, manually-run end-to-end pass: real search found `314159` at a real
  position, a real wallet claimed it, the transaction was independently
  confirmed on-chain (`ownerOf`, `tokenIdToDiscoveryId`), the indexer picked
  up the event and updated Postgres, and the public discovery page rendered
  the correct CLAIMED state — now codified as a committed Playwright test.

Explicitly deferred, not faked:

* **Mainnet/testnet deployment.** Everything above runs against a local
  Hardhat chain. Deploying to Base Sepolia needs a real funded
  `DEPLOYER_PRIVATE_KEY`, which isn't something to generate or fund
  automatically — see `.env.example`.
* **IPFS/decentralized storage for metadata.** `apps/api` serves metadata
  and artwork directly (both fully deterministic, reproducible from
  discovery data — see `docs/architecture.md` §37-equivalent). Pinning to
  IPFS is a deployment-time step gated on `STORAGE_PROVIDER` credentials,
  not implemented here.
* **`apps/admin`** (protected dashboard, spec §35) — not built. The
  underlying data it would show (dataset status, search/claim counts,
  failure rates) already exists in Postgres and the API; this is a thin
  UI layer on top, lowest priority once the core loop was proven.
* **Daily challenges, share-challenge links, search history for anonymous
  users** (spec §21/§49) — the rarity/achievability math they depend on
  (`packages/pi-core`'s `pickAchievableChallengeLength`) is implemented and
  tested; wiring it into scheduled challenge generation and localStorage-based
  history is straightforward but not done.
* **WalletConnect** — only the injected-wallet connector is wired
  (MetaMask/Coinbase Wallet/etc. via `window.ethereum`); WalletConnect needs
  a project ID the user must supply.
* **Full FM-index.** `packages/pi-search` uses a suffix array (prefix
  doubling), not the FM-index originally discussed — a documented,
  deliberate substitution given the dataset's actual size; see
  `packages/pi-search`'s module docs.

## Build order (all phases touched)

Following [`agent_prompt.md`](agent_prompt.md) §53:

1. **Foundation** — monorepo, TypeScript, Next.js, Postgres, env config.
2. **π engine** — real generation, chunking/commitment, search, independent-verify script.
3. **Core product** — conversion modes, search UI wired to a real backend, rarity/achievability.
4. **Smart contract** — `PiHunterNFT`/`PiDatasetRegistry`/`MerkleVerifierV1`, 14 tests, deploy script.
5. **Proof system** — end-to-end wiring, verified live on-chain.
6. **NFT** — deterministic metadata + SVG artwork, tokenURI.
7. **Social** — discovery pages, dynamic OG images, sharing.
8. **Gamification** — leaderboard, profiles, computed achievements.
9. **Hardening** — rate limiting, a global error handler (added after a
   real info-leak bug was found in review), Playwright E2E, this README.

## Security assumptions

The one trust assumption this architecture does not eliminate: the
published π dataset's Merkle root must have been honestly computed from
real π. This is not solved by cryptography — it's made independently
auditable (`pnpm --filter @pi-hunter/pi-search verify` regenerates
everything from scratch). Full detail in `docs/proof-system.md` §5 and
`docs/threat-model.md` T3.
